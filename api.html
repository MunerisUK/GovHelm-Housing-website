Documentation

API reference

One REST API over the whole platform, described by an OpenAPI 3.1 specification and paired with a signed event stream. This page covers the conventions; the specification covers every field.

Try it in an evaluation

Conventions

The API is deliberately boring. If you have used a well-behaved REST API before, there is nothing to learn here.

  • Base path — /api/v1, versioned in the path
  • Identifiers — prefixed, sortable strings such as app_01J9Z2K7QH
  • Pagination — cursor based, ?cursor=&limit=, with meta.next_cursor
  • Filtering — explicit query parameters per resource, never a generic query language
  • Concurrency — ETag on reads, If-Match required on updates
  • Idempotency — Idempotency-Key on every POST that creates something
  • Errors — RFC 9457 problem documents with a stable type URI
  • Times — RFC 3339 in UTC; dates without times are plain YYYY-MM-DD

Authentication

Two token types. Service integrations use OAuth 2.0 client credentials with scopes granted per integration. User-delegated access uses the signed-in person's token, and inherits their role exactly — an integration acting for a user can never see more than the user can.

Requesting a service token

POST /oauth/token HTTP/1.1
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=finance-bridge
&client_secret=***
&scope=tenancies:read charges:write

Every resource supports the standard collection and item operations unless noted. Write operations are subject to the same scheme rules and validation as the user interface.

Errors

Errors are problem documents. Validation failures list every field that failed rather than stopping at the first, because a form that reports one error at a time is an accessibility problem as much as an API one.

Validation error

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://ihap.dev/problems/validation-failed",
  "title": "The application could not be submitted",
  "status": 422,
  "detail": "2 fields failed validation",
  "instance": "/api/v1/applications",
  "errors": [
    { "field": "household.members[1].date_of_birth",
      "code": "date_in_future",
      "message": "Date of birth cannot be in the future" },
    { "field": "current_address.uprn",
      "code": "not_found",
      "message": "No property matches this UPRN" }
  ]
}

Event catalogue

Around ninety event types are published. The naming is aggregate.past_tense_verb, and every event carries the aggregate identifier, the actor and a correlation identifier.

EventFires when
application.submittedAn applicant or officer submits an application
application.withdrawnAn application is withdrawn or cancelled
assessment.band_changedA banding decision is made or revised
advert.cycle_closedA lettings cycle closes and bidding stops
shortlist.publishedA shortlist is produced for a cycle
offer.acceptedAn applicant accepts an offer
case.duty_acceptedA homelessness duty is accepted
case.duty_endedA duty ends, with the reason code
tenancy.startedA tenancy begins
tenancy.endedA tenancy terminates, with the reason
charge.raisedA rent or service charge is raised
document.generatedA letter or notice is produced

Rate limits and stability

  • Default 600 requests per minute per client, configurable per deployment; limits are returned in RateLimit headers
  • Bulk reads should use the event replay endpoint or a read replica rather than paging the whole collection
  • From 1.0, v1 is stable: no breaking changes without a major version and six months' notice, which is written into the licence terms
  • Additive changes — new fields, new endpoints, new event types — can happen in any minor release, so clients must ignore unknown fields

The specification is authoritative

This page describes the shape of the API. The OpenAPI 3.1 document describes every field, ships with each release and is served by your own instance at /openapi.json. Generate a client from it rather than writing one by hand.
