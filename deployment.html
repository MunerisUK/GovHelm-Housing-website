Documentation

Deployment

Reference topologies, sizing guidance and the operational procedures you will need before anyone depends on the system. Written for a platform team that wants to run it themselves.

  • Single VM to Kubernetes
  • No phone-home
  • Your infrastructure, or managed by us

Reference topologies

Three shapes, depending on scale and appetite

Evaluation & small providers

Single host

Everything in one Docker Compose stack on a single virtual machine with managed backups. Suitable for pilots, and for providers under roughly 2,000 units who accept a restore-from-backup recovery.

Most common

Managed services

Application containers on your container platform, with managed PostgreSQL, object storage and message broker from your cloud provider. The best balance of operational effort and resilience.

Large & shared services

Full Kubernetes

Helm charts, horizontal scaling per service, multi-zone PostgreSQL and a separate read replica for reporting. For large providers and sub-regional partnerships.

The application does not change

The same container images run in all three topologies. Moving between them is a configuration and operations exercise, not a migration, so starting small does not paint you into a corner.

Installation

Same shape whichever topology you choose

  1. 1

    Provision dependencies

    PostgreSQL 16+, S3-compatible object storage, an OpenSearch-compatible index and a message broker. Managed services are fine and recommended.

  2. 2

    Configure secrets

    Database credentials, storage keys, the identity provider client and the webhook signing keys go into your secret manager. Nothing goes in an image.

  3. 3

    Apply configuration

    Scheme rules, case types, templates and roles are applied from your configuration repository, validated before they take effect.

  4. 4

    Run migrations

    The schema migration job runs to completion before application containers start. Migrations are forward-only and idempotent.

  5. 5

    Connect identity

    Register GovHelm Housing with your identity provider and map groups to roles. Test with a real account before opening it up.

  6. 6

    Verify

    The bundled verification suite checks connectivity, permissions, storage, search, event delivery and backup readiness, and prints a pass or fail report.

Terminal

# Kubernetes, using the published chart
helm repo add govhelm https://charts.govhelm.dev
helm repo update

helm upgrade --install govhelm govhelm/govhelm \
  --namespace govhelm --create-namespace \
  --values values.production.yaml \
  --set image.tag=1.0.0

# run the verification suite
kubectl -n govhelm create job verify-install \
  --from=cronjob/govhelm-verify
kubectl -n govhelm logs job/verify-install -f

values.production.yaml (extract)

govhelm:
  environment: production
  baseUrl: https://housing.example.gov.uk
  modules:
    register: true
    allocations: true
    lettings: true
    casework: true
    tenancy: true
    income: false          # finance system stays in place
  identity:
    issuer: https://login.example.gov.uk
    clientIdRef: govhelm-oidc-client
  retention:
    enforce: true
    dryRun: false

Operations

The parts that matter at three in the morning

Backup and restore

Point-in-time recovery on the database, versioned object storage and a documented restore runbook. Restore is tested by the project on every release; test yours quarterly.

Upgrades

Rolling upgrade with backward-compatible migrations. Each release documents its steps and any action required before or after.

Monitoring

Structured logs, Prometheus-compatible metrics and traces on open standards, with starter dashboards and alert rules supplied.

Business continuity

Documented recovery point and time objectives per topology, and a read-only degraded mode so residents can still see their status during an incident.

Environments

Production, staging and a training environment with anonymised data. The anonymisation tooling is included, and non-production environments are not separately licensed.

Patching

Critical security fixes within five working days of release, with a published advisory. Minor releases roughly every eight weeks.

Before go-live

The checklist we would want to see

  • Restore tested from backup into a clean environment, with a signed-off report
  • Penetration test completed against your deployment, not just the project's
  • Accessibility statement published for your instance
  • Data protection impact assessment completed and signed off
  • Retention schedules configured and verified in dry-run mode first
  • Role assignments reviewed by the service, not only by IT
  • Audit log export to your SIEM confirmed working end to end
  • Scheme configuration signed off by the service and legal
  • Migration reconciliation report accepted by the service
  • Assisted digital route staffed and tested
  • Incident and escalation routes agreed, and the support contact tested
  • Degraded-mode behaviour rehearsed with the service desk
