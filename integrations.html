Integrations

IHAP is designed to sit in an estate it does not control. Everything it knows is available over a documented API, and everything that happens is available as an event.

API referenceTalk to us about your estate

Three ways in

Pick the one that matches the problem

Synchronous

REST API

Read and write every resource the platform holds, described by an OpenAPI 3.1 specification and secured with OAuth 2.0 client credentials or a user token.

API reference

Asynchronous

Webhooks and events

Subscribe to domain events — application submitted, band changed, offer accepted, tenancy started — delivered with signature verification, retries and a replayable log.

Scheduled

Batch and file transfer

Scheduled import and export jobs for the systems that still speak CSV or fixed-width files, with validation reports and reconciliation.

Working with the API

A request is a request

Every resource follows the same conventions: plural nouns, cursor pagination, If-Match for optimistic concurrency, RFC 9457 problem documents for errors, and an Idempotency-Key header on anything that creates something.

Reads are filtered by the calling client's scopes in the same way the user interface filters by role, so an integration cannot see more than the person or service it acts for.

The specification is published with each release and served by your own instance, so you can generate a client rather than write one.

The platform tells you what happened

Example webhook delivery

POST /your-endpoint HTTP/1.1
X-IHAP-Event: tenancy.started
X-IHAP-Delivery: dlv_01J9ZB4M2X
X-IHAP-Signature: sha256=9f2c...

{
  "event": "tenancy.started",
  "occurred_at": "2026-09-08T11:02:17Z",
  "tenancy_id": "ten_01J9ZB3PQ4",
  "property": { "uprn": "100023336956" },
  "household_id": "hh_01J9Y8M4RB",
  "tenancy_type": "introductory",
  "start_date": "2026-09-08"
}

Delivery guarantees

  • At least once. Handle duplicates using the delivery identifier; every event carries one.
  • Signed. HMAC-SHA256 over the raw body with a per-subscription secret you rotate.
  • Retried. Exponential backoff for 24 hours, then parked in a dead-letter queue you can inspect and replay.
  • Ordered per aggregate. Events for a single case or tenancy are delivered in sequence.
  • Replayable. Re-request any window of events, which makes rebuilding a downstream index straightforward.

Around ninety event types are published. The full catalogue is in the API reference.

Migration from an incumbent system

The integration that matters most

  1. 1

    Profile the source

    Extract and profile the incumbent data before agreeing anything. Duplicate parties, orphaned tenancies and addresses without UPRNs are found here, not at go-live.

  2. 2

    Map to the core model

    Party, household, property, case, tenancy and scheme. The mapping is written as configuration and reviewed by the service, not just by IT.

  3. 3

    Load, reconcile, repeat

    Trial loads run as often as needed. Each produces a reconciliation report the service signs off: counts, exceptions and sampled records.

  4. 4

    Run in parallel

    New applications flow into IHAP while the incumbent stays readable. Cut over one service area at a time.

  5. 5

    Archive with the audit trail

    The historic record is loaded with its provenance so a past decision can still be explained after the old system is switched off.

Migration tooling is included

The loaders, the profiling reports and the reconciliation tooling come with the licence. Migration is the part of a housing implementation most often sold as a separate project; here the tooling is simply part of the product.
