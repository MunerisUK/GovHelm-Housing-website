Architecture

GovHelm Housing is deliberately unexciting technology arranged carefully. This page explains the layers, the data model at the centre, and the decisions behind both.

Deployment topologiesAPI reference

Layers

Four layers, each with a documented boundary. Presentation talks only to the API gateway. Modules talk to the core and to each other through events, never through each other's database tables. The core owns the shared data model.

That last rule is the one that keeps the platform coherent. A module may not read another module's tables directly; it asks the core or subscribes to an event. It is a constraint that costs a little effort up front and saves a rewrite later.

The core data model

Six entities everything else hangs from

If you read nothing else about the architecture, read this. The data model is the part that is expensive to change, so it is the part we thought hardest about.

EntityWhat it holdsWhy it is in the core
PartyPeople and organisations, with identifiers, contact details and relationshipsApplicants become tenants become former tenants. One identity across all of it.
HouseholdA composition of parties at a point in time, with roles and dependencyHousing need is assessed for a household, which changes over time and must be reconstructible for any past decision.
PropertyAddresses keyed on UPRN, with scheme, block and attribute hierarchyAllocations, tenancies, repairs and returns all reference the same property.
CaseA unit of work with a type, status, statutory clock and decision historyApplications, homelessness duties, reviews and appeals are all cases with different rules, not different systems.
TenancyAn agreement linking a household to a property, with type, dates and chargesThe spine of everything after a let.
SchemeVersioned allocation policy: bands, criteria, quotas and local rulesA decision must be explainable against the scheme in force when it was made.

Versioning is not optional

Scheme, household and case records are all temporal: the platform keeps the state as it was, not merely the state as it is. When an applicant challenges a banding decision made two years ago, the system can show the scheme version, the household composition and the evidence as they stood on the day.

Technology choices

And the reasoning behind each

ChoiceWhat we useWhy
Data storePostgreSQL 16+Mature, well understood by public sector DBAs, strong support for temporal data and JSON alongside relational.
RuntimeContainerised services (OCI images)Deployable on a single VM with Docker Compose or on Kubernetes, without changing the application.
API styleREST over HTTPS, described in OpenAPI 3.1Toolable, cacheable, and readable by people who are not developers. Generated clients in any language.
EventingTransactional outbox to a message brokerModules stay decoupled and integrations get a reliable event stream without dual-write bugs.
IdentityOpenID Connect, with SAML 2.0 for legacy estatesPlugs into your existing directory. GovHelm Housing never becomes your password store for staff.
DocumentsS3-compatible object storageWorks with AWS, Azure via gateway, MinIO on-premises. Evidence never lives in the database.
SearchOpenSearch-compatible indexFast person and property search across millions of records without loading the transactional database.
Front endServer-rendered HTML with progressive enhancementWorks on old devices and poor connections, which is exactly who applies for housing.

Cross-cutting concerns

Handled once, in the core

Permissions

Role-based, resolved centrally, enforced at the API boundary and again at the query layer. Field-level redaction for restricted case types.

Audit

Append-only log of every read and write with actor, time, reason and request correlation identifier. Exportable, never editable.

Workflow

Statutory clocks, escalation and review scheduling driven by the case type definition rather than hard-coded per module.

Notifications

One delivery pipeline for email, SMS, letter and portal message, with template versioning and delivery receipts.

Retention

Retention rules evaluated against case closure dates, with legal hold and a reviewable deletion log.

Observability

Structured logs, metrics and traces on open standards, so it fits whatever monitoring you already run.
