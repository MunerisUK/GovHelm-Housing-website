Milestones on GitHub

Release plan

Where the project is

  1. Shipped · 0.7

    Core platform and housing register

    The foundations: party and household model, property register keyed on UPRN, case and workflow engine, permissions and audit.

    • Applications and registration module
    • Needs assessment with configurable banding rules
    • Staff workspace with work queues
    • OIDC single sign-on and role management

  2. Shipped · 0.8

    Allocations, lettings and the citizen portal

    The first end-to-end journey, from online application through to an offer.

    • Allocations and shortlisting against scheme rules
    • Choice-based lettings with advert cycles and bidding
    • Citizen portal at WCAG 2.2 AA
    • Documents and correspondence with template versioning

  3. In progress · 0.9

    Homelessness casework and statutory returns

    Current focus. The Homelessness Reduction Act duty sequence as a first-class part of the model rather than a bolt-on register.

    • Prevention, relief and main duty casework
    • Personalised Housing Plans with task tracking
    • Temporary accommodation placement and charging
    • H-CLIC and CORE return preparation with validation
    • Duty-to-refer inbox

  4. Next · 1.0

    Tenancy, income and the stable API

    The first release with a supported upgrade path and a versioned public API contract.

    • Tenancy management through to termination
    • Income, rents and arrears with pre-action protocol steps
    • API v1 declared stable with a deprecation policy
    • Migration tooling and reconciliation reporting
    • Published penetration test results

  5. Planned · 1.1

    Assets, compliance and analytics

    Closing the loop with stock and compliance data.

    • Repairs and asset interface with compliance flags
    • Void turnaround tracking through to re-let
    • Tenant satisfaction measures reporting
    • Operational dashboards for service managers

  6. Planned · 1.2

    Partnerships and sub-regional working

    Support for several organisations presenting one scheme to residents.

    • Multi-organisation tenancy and nomination flows
    • Shared sub-regional choice-based lettings
    • Partner portal with scoped access
    • Cross-boundary reporting

How the roadmap is decided

Openly, and with the people running it

Anyone can propose work by opening an issue. Proposals that change the data model, the API contract or the scope of a module are written up as a design note and discussed in public before any code is written.

The technical steering group meets monthly, reviews open design notes, and publishes its decisions with reasoning in the repository. Organisations running IHAP in production have a seat; so does the maintainer team.

Two things reliably move work up the list: a statutory deadline that affects every provider, and a contributor willing to do the work. The second is more effective than the first.

See governance for how the steering group is constituted and how decisions are recorded.

Explicitly not planned

Being clear about scope is as useful as being clear about the plan.

  • A general ledger. IHAP raises charges and posts to your finance system.
  • Asset and works management. IHAP interfaces with yours.
  • A contact centre or corporate CRM.
  • A hosted service run by the project. Suppliers may offer one; the project does not.
  • Non-UK housing legislation in the core. Forks are welcome.

Versioning and support

What a version number promises

ElementPolicy
Release cadenceA minor release roughly every eight weeks; patch releases as needed.
Semantic versioningFrom 1.0, the public API and database schema follow semantic versioning.
API stabilityBreaking API changes only in a major version, with at least six months' notice.
DeprecationDeprecated endpoints keep working for two minor versions and are announced in release notes.
Security patchesCritical fixes released for the current minor version and the one before it.
Upgrade pathEvery release documents its migration steps; schema migrations are forward-only and reversible within a release.
Long-term supportFrom 1.0, one release per year is designated LTS with twelve months of security fixes.
