Contributing

How to get a change into IHAP, from a typo in the documentation to a new module. The process is deliberately light, and deliberately public.

CONTRIBUTING.md

Your first contribution

Fork, branch, change, test, open a pull request. If you have contributed to any open source project before, there is nothing unusual here.

Issues labelled good first issue are scoped small and have enough context to start without asking. Documentation fixes are genuinely welcome and are reviewed with the same care as code.

Terminal

git clone https://github.com/your-account/ihap.git
cd ihap
make dev-setup          # installs hooks, pulls images, seeds the dev database
make test               # unit and integration tests
make check              # lint, format, accessibility and schema checks

git switch -c fix/banding-effective-date
# ... make your change, add a test ...
make test check
git commit -m "fix(assessment): use scheme version in force at decision date"
git push origin fix/banding-effective-date

What a reviewer will look for

  • A test that fails without your change. The most useful part of most pull requests.
  • Accessibility. Any interface change is checked against WCAG 2.2 AA. Automated checks run in CI; a reviewer will also use a keyboard.
  • The audit trail. If your change alters a decision, the decision record has to explain itself.
  • Data model discipline. Modules do not read each other's tables. If you need data from another module, use the core or an event.
  • Migration safety. Schema changes must be backward compatible within a release so a rolling upgrade works.
  • Plain English. Resident-facing text gets a content review.

Larger changes

Anything that changes the data model, the public API, the scope of a module or the behaviour of a statutory process starts as a design note, not a pull request. A design note is a short markdown document describing the problem, the options considered, the recommendation and the migration consequences.

Open it as a pull request against docs/design/ so it can be discussed in line. The steering group reviews open notes monthly and records a decision with reasoning. Once accepted, the implementation pull request references it.

This exists to stop good work being wasted. A rejected design note costs a day; a rejected three-month implementation costs considerably more.

Licensing and provenance

Contributions are accepted under the Apache License 2.0, the same licence as the project. There is no copyright assignment and no contributor licence agreement to sign; the project uses the Developer Certificate of Origin, so sign off your commits with git commit -s.

If you are contributing on behalf of an employer, please make sure you have their agreement. For public sector staff this is usually straightforward, but it is easier to establish before the pull request than after.

Issue labels

How work is triaged

LabelMeaningResponse
good first issueSmall, scoped, well describedClaim it by commenting; no need to ask
help wantedAgreed work nobody is doingComment before starting so effort is not duplicated
design note neededToo significant for a direct pull requestWrite the note first
statutoryDriven by legislation or a return specificationPrioritised against the deadline
accessibilityA barrier to completing a taskTreated as a defect, not an enhancement
securityOnly used after private disclosureNever open a security issue publicly first
needs practitioner inputA question about how a duty worksHousing practitioners especially welcome
blockedWaiting on a decision or another changeThe blocking item is linked

Release process

How your change reaches a deployment

  1. 1

    Merged to main

    Once approved and green in CI. Main is always releasable; long-lived feature branches are avoided.

  2. 2

    Release candidate

    Cut roughly every eight weeks. Accessibility and security testing run against the candidate, and providers are invited to test against their own configuration.

  3. 3

    Release notes

    Every change is listed, with a migration section, a security section and credit to contributors, including non-code contributions.

  4. 4

    Published

    Signed container images, Helm chart, OpenAPI specification and a software bill of materials, all tagged with the version.

  5. 5

    Supported

    Security fixes for the current minor version and the one before it. From 1.0, one release a year is designated long-term support.
